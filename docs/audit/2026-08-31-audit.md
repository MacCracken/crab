# crab — security audit, 2026-08-31

> **First audit. `docs/audit/` was empty**, which is one of crab's v1.0 criteria and the one
> `state.md` calls *"the criterion that moved furthest while nobody was looking at it"*.
>
> **Scope**: the working tree at M5 (post-gallery), against `crab_render`'s inputs and every path
> that touches data crab did not author — readdir records, file bytes, image headers, EXIF, and the
> names the operator types.
> **Method**: read every parser and guard, then verify each claim against the code rather than the
> comment. Findings are ranked by what an attacker gets, not by how interesting the bug is.
> ⚠ **This is a code audit, not a penetration test.** Nothing here was exploited; where a finding
> says "would", it means the code path admits it, not that it was demonstrated.
>
> ⛔⛔ **ONE FINDING IN THE FIRST DRAFT WAS WRONG (F3), AND IT IS KEPT WITH ITS CORRECTION RATHER
> THAN DELETED.** It claimed an unbounded read that the code could not perform. It was caught by
> planting the mutation the finding implied and watching the suite stay green, then proving it
> empirically with a poison tail. **An audit that reports a bug which is not there spends the
> reader's trust and sends them to "fix" working code** — so the process that caught it belongs in
> the document as much as the findings do. Everything else here was re-derived afterwards.

## The trust model, stated once

crab is a **local, single-user** file manager. It has no network surface (`net` is a redundant
stdlib declaration; setu's transport is a local channel band). The data it does not author is:

1. **readdir records** from the kernel — 64-byte fixed records, name at +0, type at +63.
2. **file contents** — read for image headers, EXIF, thumbnails and the copy path.
3. **names the operator types** — the rename field and the batch-rename pattern.
4. **argv** — two start paths.

The adversary that matters is therefore **a file placed in a directory the operator opens** — a
download, a USB stick, an extracted archive. Not a remote attacker; not another user.

---

## F1 — ⛔ **Gallery view decodes every image in a directory the operator merely opened**

**Severity: the highest finding here, and it is a change in the trust model rather than a bug.**

Before the gallery (this session), crab decoded exactly one image: the selected entry, and only with
the preview column open. **The gallery's idle-tick fill walks every entry in the active pane** and
decodes each image in index order (`src/main.cyr`, the `CRAB_VIEW_GALLERY` arm). So opening a folder
in gallery view runs the decoder over **every image in it**, including files the operator never
selected and may never look at.

crab now runs, in-process and unsandboxed on attacker-chosen bytes:

| component | lines | role |
|---|---:|---|
| `chitra` | 6,143 | PNG / JPEG / GIF / BMP decoders |
| `sankoch` | 16,373 | DEFLATE, CRC, and the rest of the compression leaf |
| crab's own | ~400 | `crab_img_dims`, `crab_jpeg_seg`, `crab_exif_*` |

**≈22,500 lines of parser reachable from a file someone else wrote.** A memory-safety bug anywhere
in it is a crab compromise, and cyrius's allocator is a bump allocator with **no guard pages**, so
an overread lands in live heap rather than faulting (measured this session — it is why the EXIF fuzz
round needed a poison tail to detect anything at all).

⭐ **Measured, not inferred** (a directory of 8 PNGs plus a `.txt`, 2026-08-31):

| path | files decoded | permanent bytes |
|---|---:|---:|
| preview (one entry selected) | **1** | 165,256 |
| gallery fill (folder merely opened) | **8** | 1,033,768 |

⇒ **8× the decoder invocations and 6× the unreclaimable memory, for the same operator action of
opening a folder.** The exposure change is the finding; the memory is only its shadow.

**What already limits it**, honestly:
- The per-image budget (`CRAB_THUMB_MAX_RGBA`, 4 MB) refuses from the **header**, before allocating.
- The session ceiling (`CRAB_THUMB_TOTAL_MAX`, 32 MB) stops decoding entirely once spent.
- Refusals are cached, so a hostile file is decoded at most once per listing.
- `crab_is_image` gates on extension, so only files *named* like images are opened at all.

⛔ **All four bound MEMORY. None bounds CODE PATHS REACHED.** A crafted 64×64 PNG passes every budget
and reaches the full inflate and unfilter path.

**Recommendation (operator's call, not a defect to fix silently):**
1. Consider making the gallery's fill **opt-in per directory**, or limited to entries the operator
   has scrolled to, so "open a folder" is not "parse every image in it".
2. chitra ships a fuzz harness; crab's exposure is now large enough that its coverage is crab's
   concern too.
3. When agnos gains process isolation cheap enough to use, decoding is the first thing that should
   leave crab's address space.

## F2 — ⚠ TOCTOU between the ELF check and the spawn

`crab_fs_launch` (`src/app.cyr`) opens the target, reads four magic bytes, closes it, and then calls
`sys_spawn_path` — which opens it again. Between those two opens the file can be replaced.

**Severity: low, and bounded by what it is for.** The ELF check is a **UX gate** — "do not try to
run a text file" — not a security boundary: crab will happily spawn any ELF the operator selects, so
winning the race buys the attacker the ability to run a *different* ELF in a directory they can
already write to. Nothing crosses a privilege boundary.

⚠ Recorded because the shape is the dangerous one, and because the fix has no cheap form today:
agnos has no `fexecve` and `spawn_path`(43) takes a path, so there is no way to spawn the descriptor
that was checked.

## F3 — ⚠ `crab_batch_name` had no fuzz coverage, and a claim about it that was **wrong**

The batch-rename sheet expands a pattern where `*` splices in **a readdir name** — data crab did not
author — and `#` a sequence number. The result goes to `crab_fs_rename`.

⛔⛔ **THIS ENTRY'S FIRST DRAFT REPORTED AN UNBOUNDED READ. THAT WAS WRONG, AND THE CORRECTION IS
KEPT HERE RATHER THAN QUIETLY DELETED.** The splice loop has no explicit bound on its read index, and
`orig` is a 64-byte record the kernel is trusted to terminate — which is exactly the shape of the
`crab_name_cell` defect from 0.7.1, and is why it looked like one. **But `w` and `j` increment
together and `w` starts at or above `j`**, so the destination check `w >= lim` trips at `w == 63`
before `j` can reach 64. The read is already confined to indices 0..63 of a 64-byte record, **by the
destination cap**.

⭐ **Verified empirically, not by re-reading**: the guard was removed, an unterminated 64-byte record
followed by a poison run was pushed through, and **no poison reached the output**. A mutation
deleting the guard also passes the suite — which is how the false finding was caught at all.

⇒ **What is real** is that the safety is a **coincidence of two constants that can move
independently**: `CRAB_EDIT_CAP` (64) and `CRAB_NAME_MAX` (64). Raise the edit cap alone and the
overread becomes real, silently. So:
- the `j >= CRAB_NAME_MAX` guard is **kept as defence in depth**, and its comment says it is
  unreachable today rather than pretending it fixed something;
- `tests/crab.tcyr` now **asserts `CRAB_EDIT_CAP <= CRAB_NAME_MAX`**, so that change cannot pass
  unnoticed.

⚠ **The coverage gap was real and is closed.** `tests/crab.fcyr` now drives `crab_batch_name` —
arbitrary patterns biased toward `*` and `#`, half the records unterminated — asserting that any
accepted name is NUL-terminated inside the cap, that a *refused* one still leaves a valid cstring,
and that whatever comes out still faces `crab_name_ok`. It was the last parser over non-authored
bytes with none.

⛔ **The lesson is the finding.** An audit that reports a bug which is not there is worse than one
that reports nothing: it spends the reader's trust and sends them to "fix" working code. Every
finding above was re-derived against the code after this one was caught.

## F4 — ⚠ A `DT_UNKNOWN` readdir type would make a recursive delete report a failure

The record's type byte is set from `DT_DIR` on the host and `ftype == 2` on agnos; anything else
leaves 0. Filesystems that answer `DT_UNKNOWN` (0) exist, and on one of those a real directory
arrives as type 0, the walk treats it as a leaf, and `unlink` on a directory fails.

**Severity: low, and it fails SAFE** — the operation reports an error instead of deleting the wrong
thing. Recorded because the same byte is the descend gate (see the note below), so its trustworthiness
matters more than a correctness bug usually would.

## What was checked and found sound

Listed because an audit that reports only findings gives no evidence of coverage.

- ⭐ **Symlinks cannot be descended into by a recursive delete, and it is safe by construction rather
  than by a check.** Both kernel backends set the type byte from "is a directory" alone, so a symlink
  — including one pointing at a directory — arrives as type 0 and the walk unlinks the **link**,
  never the target. That is correct `rm -r` behaviour achieved with **no `lstat`**, which does not
  exist in the pinned stdlib. `src/app.cyr` documents it at the descend gate.
- ⭐ **No shell is invoked anywhere.** `sys_spawn_path` takes a path and an argument count; there is
  no `sys_system`, so there is no command injection surface. (CLAUDE.md forbids `sys_system` with
  unsanitized input; crab does not call it at all.)
- **`crab_name_ok` is the single guard between a keypress and `unlink`**, and it rejects: a null
  pointer, an unterminated 64-byte record, the empty name, `.`, `..`, and any name containing `/`.
  Every write entry point routes through it.
- **Every path join is bounded.** `crab_join_n` / `crab_strcpy_n` / `crab_cstr_len` all take a cap
  and report truncation as `-1` rather than silently producing a shorter path; `CRAB_PATH_MAX` is
  256 and the walk's depth bound is provably unreachable before the join refuses.
- **The image and EXIF parsers are bounded at their absolute addresses**, iteration-capped, and
  fuzzed — 60,000 deterministic rounds with a poison tail that detects reads past the declared
  length. Two guards are **not** detectable that way and the harness says which and why.
- **Arithmetic**: `crab_surface_bytes` bounds both dimensions and the product; `crab_dims_ok` bounds
  width and height to an absurdity limit; `crab_op_eta` guards `rate <= 0` before dividing;
  the EXIF entry offsets are `i64` against `u32` inputs, so none can overflow.
- **The thumbnail cache's slot layout does not overlap**: `CRAB_TC_PATH` is 0 with
  `CRAB_PATH_MAX` = 256 bytes, and `CRAB_TC_STATE` begins at 256.
- **Resource exhaustion is bounded** in every loop that reads non-authored data: the readdir walk
  has a stall detector and a step cap, the JPEG marker walk an iteration cap, the EXIF directory an
  entry cap, and the decode two budgets.

## What this audit did NOT cover

- **The agnos-only paths were read, not run.** Every `#ifdef CYRIUS_TARGET_AGNOS` region — the event
  loop, the `#101` readdir walk, spawn — is invisible to the host suite by construction.
- **chitra and sankoch were not audited.** Their line counts are given in F1 as inherited surface;
  their correctness is their own repos'.
- **No fuzzing of the write layer's joins**, and none of `crab_batch_name` (F3).
- **No timing or side-channel analysis.** Not meaningful for a local single-user file manager.

## Standing hazards recorded elsewhere, repeated here because they bear on safety

- ⛔ **`crab_fs_open_w` has no overwrite guard on the shipping target.** The host arm is
  `O_WRONLY|O_CREAT|O_EXCL`; the agnos arm is `AO_WRONLY|AO_CREAT|AO_TRUNC` because **agnos has no
  `AO_EXCL`**. So a recursive copy that collides truncates rather than refusing, on agnos only.
  Filed: `agnos/docs/development/issues/2026-08-31-open-ao-excl-flag.md`.
- ⚠ **Decoded memory is never reclaimed.** `chitra_image_free` is a no-op and cyrius's `alloc` has no
  `free()`, so a decode costs ~2.5× the image's RGBA size permanently. The two budgets exist for
  that reason and are load-bearing, not tidiness.
